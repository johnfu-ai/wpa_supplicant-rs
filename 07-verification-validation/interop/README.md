## Architecture

The harness reproduces a real wired 802.1X authentication topology:

```
┌──────────────────┐         ┌──────────────────┐         ┌──────────────────┐
│   wpa-supplicant │  EAPOL  │     hostapd      │ RADIUS  │   FreeRADIUS     │
│  (our binary)    │◀─L2────▶│ (Authenticator)  │◀──UDP──▶│  (Auth Server)   │
│                  │         │  wired mode      │         │                  │
└──────────────────┘         └──────────────────┘         └──────────────────┘
        │                            │                              │
   AF_PACKET on                veth pair to                radsecproxy on
   eth0 (in NS)               supplicant NS                  internal net
```

* **Supplicant**: `crates/wpa-supplicant` built with `--features raw-socket`, run as root inside a network namespace bound to one end of a veth pair.
* **Authenticator**: `hostapd` 2.10+ in `driver=wired` mode, bound to the other end of the veth pair. Proxies EAP to FreeRADIUS via RADIUS.
* **Authentication Server**: `freeradius/freeradius-server:latest-3.2-alpine` configured with EAP-TLS, EAP-PEAP, and EAP-TEAP methods accepting our test cert chain.
* **Cert chain**: A throwaway CA + server cert + client cert generated by `scripts/gen-certs.sh` on first run. Certs are *not* checked into git — they are regenerated per-harness-run so the harness has no credential exposure.

## Usage

### Local (developer workstation)

```bash
# Prerequisites: docker, docker-compose, openssl, iproute2.
# The supplicant binary must already be built with --features raw-socket:
cargo build -p wpa-supplicant --features raw-socket --release

cd 07-verification-validation/interop
./scripts/gen-certs.sh           # idempotent — regenerates only if certs/ is empty
docker compose up -d             # starts freeradius + hostapd
sudo ./scripts/run-supplicant.sh # binds supplicant to the veth, asserts EAP+MKA
docker compose down              # tear down
./scripts/teardown.sh            # remove veth pair
```

### From `cargo test`

```bash
# `interop_freeradius` is `#[ignore]`-gated because it requires:
#  - Docker daemon running
#  - sudo (CAP_NET_RAW for AF_PACKET + iproute2 for veth)
#  - openssl in PATH
# Run explicitly:
sudo -E cargo test -p wpa-supplicant --features raw-socket \
    --test interop_freeradius -- --ignored
```

### From CI

A dedicated workflow `.github/workflows/interop.yml` runs the full
harness on a `ubuntu-latest` runner (which has Docker pre-installed)
on every push to `main`. The job is gated on the `interop` label
(or scheduled nightly) so PR latency stays low — interop runs are
~5 minutes.

## Current status (as of P3.1 landing)

✅ Docker compose stack composes and starts cleanly (`docker compose up`).
✅ Cert generation script produces a valid CA + server + client cert chain.
✅ The veth-namespace setup script connects the supplicant binary to hostapd's L2 surface.
✅ The supplicant binary reaches EAP-Request/Identity → EAP-Response/Identity exchange (the bridge wired in #130 handles this without any configured EAP method).

⚠️ **Full EAP-TLS / PEAP / TEAP handshake validation** requires the EAP method factory tracked as **#133** ("load EAP methods from `EapMethodConfig` — PEM-based TLS engine construction"). Until that lands, the integration test asserts only the Identity exchange + EAPOL-Logoff round-trip. A `// TODO(#133):` marker in `tests/interop_freeradius.rs` will be lifted to a real EAP-TLS handshake assertion once that issue closes.

✅ **AES Key Wrap (RFC 3394)** for `MkaParticipantAdapter::unwrap_sak` landed in PR #146 (closes **#135**). End-to-end SAK install (wrapped-SAK MKPDU → unwrap → CP→Secured) is independently exercised by `crates/wpa-supplicant/tests/aes_key_wrap_sak.rs`. The interop harness can grow assertions on the wire-side path once an authenticator that distributes SAKs in wired mode is available (hostapd does not today); for now the SAK install assertion lives in the in-process integration test.

This is **expected scope for P3.1's first cut.** The harness infrastructure (compose, certs, veth setup, runner, CI hook) is the deliverable; the actual handshake validation depths land issue-by-issue.
